# Luna handoff: one question about the current decision

Architecture decision · 2026-10-07 · one implementation slice

## Objective

Let a player ask one question about the **current, unplayed hero decision** after explicitly opening its study preview. The answer may use external AI only when enabled locally and opted in for this exact question. Keep the practice estimate and its limitations authoritative; the model may select a validated reply plan, never provide poker numbers or prose shown as a calculated result. This is a bounded live question, not a live conversation or an automatic recommendation.

## Starting point and architectural decision

Start from merged [PR #38](https://github.com/ajpaulson18-design/openpoker-lab/pull/38), `128f6fc0dfda70b757e7a481b610d80f5fef722c`. The eighth slice provides `CurrentStudyPreviewCache` with immutable `CoachDecisionAnalysis`, a preview binding, `resolve_current_study_evidence`, a revision-checked on-demand preview route, and UI visibility/stale guards. Saved-decision one-shot and four-turn conversations remain separate and compatible. `build_grounding_bundle` currently requires a recorded choice, while a live preview has **no choice**. Extend the allowlisted grounding path additively for a choice-free preview; do not invent a fold/check/call/raise choice or copy an after-action loss into it.

Use the existing `GroundingBundle`, `CoachReplyPlan`, strict OpenAI plan selector, server-rendered reply, local teaching-note catalog where applicable, and deterministic fallback. Keep the provider disabled by default and bound by the current timeout, output limit, `store: false`, and single coach admission gate. If existing rendering uses “saved choice” language, make live labels accurate without changing saved-decision wording. The live provider prompt may need to say “current preview” rather than “saved decision”; it must still carry only the allowlisted bundle and untrusted question text.

## API and evidence rules

Add a versioned route such as `POST /api/v1/hands/{hand_id}/current-coach` with exact JSON `{target:{hand_id,decision_id,evidence_id,state_revision}, question, detail, audience}` and the existing per-request external-AI opt-in header. Require the target to match the retained preview evidence exactly. Before the provider call, verify the hand exists, is still awaiting the hero, and has the target revision; reject an expired preview with a clear refresh-preview result, a changed hand/revision with 409, unknown hand with 404, and malformed inputs with 400. The route must not accept analysis, facts, choice, prior dialogue, or model-written answer content from the browser. No new poker calculation is permitted on this route: if the preview is missing or expired, the player explicitly refreshes it first.

The choice-free grounding bundle contains current street/hero cards/board/pot, source/basis, modeled actions and their **estimated** EVs, recommendation when supplied, opponent assumptions, quality diagnostics, and mandatory limitations. It contains no `choice` or `choice_loss` fact. Mark those fields as unavailable because no action has been taken. A question about “my mistake,” “why was calling bad,” or a chosen-size loss is unavailable until an actual decision is recorded. A question about an alternative already in the modeled action set may cite its estimated EV as an alternative, but cannot compare it to a nonexistent chosen action or claim an unmodeled bet size was solved. Unsupported changed cards, ranges, bet sizes, or future streets return an explicit unanalysed response. General concepts may be taught locally without claiming the current estimate measured them.

Validate the model-selected plan against this exact bundle and permit only live-safe intents: recommendation, limits, and unavailable. If the selector asks for choice or comparison, render an explicit unavailable result or fall back locally; never imply a recorded choice. Keep required caveats and source labels outside provider text. The existing saved-decision plan path must retain its behavior and schema. Provider failures, refusals, malformed plans, disabled configuration, and admission overload return safe local responses or explicit retryable status as appropriate; no alternate provider is contacted silently. Release the coach slot on every path.

Recheck the hand/revision after the provider wait and before returning a current-decision answer. If play advanced, return `stale_context` and do not present the answer as current. Hold no `game_lock` or SQLite transaction across a provider wait. The browser also matches its active hand, revision, preview decision/evidence IDs, local request generation, and coaching visibility before rendering. Starting an action, switching hands, refreshing/changing opponent preview, or hiding coaching clears the in-flight live answer from the active panel. Keep poker controls responsive. Show question, source label, evidence-backed facts, local teaching note when valid, and limitations together. There is no automatic provider call when the preview opens.

## Scope and verification

Likely modules: `pokerlab/coach_grounding.py` for choice-free projection and safe labels; `pokerlab/server.py` for the new route and binding/lock checks; `pokerlab/coach_provider.py` only if the provider instruction must distinguish live preview from saved evidence; `pokerlab/web/app.js` and existing markup/styles for a small Ask area under the current preview; focused HTTP/grounding/UI tests. Preserve `/api/act`, saved-decision routes, existing conversation semantics, and all stored records.

Test exact binding and revision checks, missing/expired preview, no recalculation, no choice/loss leakage, recommendation/limits/unavailable intents, modeled versus unmodeled alternatives, invalid provider plans, provider timeout/disabled fallback, opt-in privacy, one provider wait concurrent with a successful hand action, stale-response rejection, Blind Play, and no gameplay-lock contention. Exercise the rendered browser flow with a fake provider and with external AI disabled. Run focused and full tests, publish one narrow PR, and stop for Sol review before merging. Do not add multi-turn live chat, streaming, automatic coaching, cancellation, persistent previews, new solver outputs, or opponent-model inference in this slice.
