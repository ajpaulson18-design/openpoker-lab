# Luna handoff: bounded follow-ups on one live preview

Architecture decision · 2026-10-08 · one implementation slice

## Objective and base

Let a player ask up to four questions about the **same current, unplayed decision**, see the turns in order, and use Simpler or Go deeper on the latest answer. Start from merged PR #42, main commit `f0c7b619678c8244c67c71c77aadce04340260e2`. The current-preview estimate, not the language model, remains the strategic authority. This slice adds continuity to the live question implemented in PR #42. Do not build a hand-wide conversation, automatic coaching, streaming, or new poker analysis.

## Boundary and API

Keep the existing `POST /api/v1/hands/{hand_id}/current-coach` one-shot route compatible. Add `POST /api/v1/hands/{hand_id}/current-coach/turns` with exact JSON `{client_turn_id, conversation_id?, target:{hand_id,decision_id,evidence_id,state_revision}, question, detail, audience}` and the existing per-request external-AI opt-in header. Return the existing bound reply and teaching note plus `conversation_id`, `client_turn_id`, and `turn_index`. Require a server-generated unpredictable conversation ID and a client-generated unpredictable turn ID. The first turn omits `conversation_id`; later turns use the returned ID. One conversation is bound to the exact immutable preview binding, including revision and evidence ID. Do not accept browser-provided history, facts, answers, plans, or choice.

Reuse `ConversationLedger` with a **separate live ledger instance** so saved-decision conversations and live previews cannot collide or consume each other's capacity. Make only the small generic ledger changes needed for accurate live errors or expiry; preserve saved-decision behavior. Cap a live conversation at four total turns and retain at most two prior validated turn summaries for the provider. A retry with the same turn ID and identical payload returns the cached result without another provider call; conflicting reuse, concurrent turns, unknown/expired conversation IDs, a fifth turn, or cross-binding reuse return explicit controlled errors. The ledger must never be the authority for poker facts: rebuild the choice-free grounding bundle from the retained preview for every accepted turn. A new conversation ID may start a fresh four-turn sequence on the same still-valid preview.

Before reserving a turn, verify the route/body, hand existence, hero turn, exact revision, and retained preview identity as the one-shot route does. Recheck these after any provider wait and before completing or returning a result, including cached retries. A changed or completed hand returns `stale_context`; expired preview returns `preview_expired` and asks for a refresh. Abort an in-flight reservation on stale/expired/provider-independent failures so it cannot replay an obsolete answer. Hold no game lock, SQLite transaction, or preview-cache lock during a provider call. Preserve the separate bounded coach admission gate and release it on all paths.

The provider still selects only a validated `CoachReplyPlan` for current-preview-safe intents: recommendation, limits, unavailable. It receives the current allowlisted bundle, this question, and at most two preceding question strings plus validated plan metadata **only when this turn explicitly opts in**. No prior reply prose, numeric answer, opponent cards, names, or user-supplied facts are sent. Each turn's rendered facts and optional teaching note come from this exact current bundle; no `choice` or `choice_loss` fact appears. Reuse the fail-closed local fallback from PR #42, including its explicit local-summary scope and unavailable chosen-action/loss behavior. A local fallback turn may be recorded, but it must not become fabricated strategy context for a later provider turn. Provider failure, invalid plan, timeout, disabled configuration, and overload keep their safe status/fallback behavior.

The retained preview's existing bounded expiry still applies. Do not silently extend or recalculate it for conversation continuity. If the player refreshes the preview and gets a new binding, start a new live conversation. Saved-decision follow-ups remain available after an action through their existing route; live turns must never be rebound to a recorded decision merely because the hand advanced.

## Browser behavior

Under the current preview, show a compact chronological list of live turns, with each question, source label, rendered facts, local teaching note, limitations, and external/local status together. Add Simpler and Go deeper controls for the latest turn; their requests retain the same binding and adjust only `audience`/`detail`. Keep the external-AI toggle off by default for every new turn and update disclosure: when opted in, the current question, allowlisted preview facts, and at most two recent questions for this same preview may be sent. No provider call occurs from opening the preview or pressing a visibility toggle.

Keep a browser conversation only for its exact preview binding. Clear the active list and in-flight generation when play starts, hand/revision changes, a different preview/opponent is selected, preview is refreshed, Blind Play hides coaching, or a new hand starts. A delayed response must match active hand, revision, decision ID, evidence ID, conversation ID, and request generation before display. If the server reports `preview_expired`, show Refresh preview; if it reports a full/expired conversation, offer Start new conversation only when the preview itself remains valid. Gameplay must remain responsive while a turn is pending. Render all text escaped and retain the existing saved-decision conversation UI unchanged.
